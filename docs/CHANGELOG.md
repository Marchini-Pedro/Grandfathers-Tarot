## 1.5.5
- **Twin captains spawned without their void shield.** Cause (game source): both twins use toughness template `twin_captain_one` with `start_depleted = true` (`minion_toughness_templates.lua:64-73`), so the shield is created DOWN (`minion_toughness_extension.lua:17-25`). The game raises it right after spawning: `optional_init_toughness` in the spawn param table makes `MinionSpawnManager.spawn_minion` call `toughness_extension:set_toughness_damage(0, true)` (`minion_spawn_manager.lua:211-218`; the auto event sets it for its twins, `auto_event.lua:845-883`; the toxic-gas-twins mutator calls `set_toughness_damage(0, true)` directly, `mutator_toxic_gas_twins.lua:810-834`). We spawned with `spawn_minion` and never set it. Fix (`spawn/execute.lua`, `needs_shield_init`): any breed whose `toughness_template.start_depleted` is true (only the twins) gets `param.optional_init_toughness = true`. Not verified in game (matrix row 46).

## 1.5.3
- **Typing in the editor no longer triggers keybinds** (pressing "i" while typing opened the inventory). Cause: DMF evaluates every mod's keybinds from the raw keyboard state each frame in `dmf.check_keybinds()` (`dmf_loader.lua:66`, `keybindings.lua:309`; its input-service check is a stub that always returns true, `keybindings.lua:48-51`), with no notion of a focused text field. `hub_hotkey_menus` (view-toggle keybind on "i", it only checks the chat and its own view, `hub_hotkey_menus.lua:48`), F-keys and every other DMF keybind therefore fired while typing. The vanilla hotkeys were NOT involved (they are blocked while any view is open, `ui_manager.lua:548-575`). Fix: while any of the editor's popups (rename, numbers, recipe text, search) is open a flag is set (`mod.rw.text_input_active`), and a hook on `dmf.check_keybinds` (installed in `on_all_mods_loaded`) skips the whole keybind check. This suspends ALL mods' keybinds only while a text box is open; it releases on confirm, cancel, Esc and when the editor is closed, and a reloaded (stale) instance can never block keys (`RW.dead`).
- Tests: new `tools/entry_test.py` (9 checks: loads the real entry script with stubs, checks the hook, its pass-through/skip behaviour, unload, bypass hooks, view and command registration); editor 129 (the flag follows every popup open/close, including closing the whole editor).

## 1.5.0
- **"Same" tick box for repeating waves:** each enemy group on the detail screen has a tick box (column "Same", right of the repeat stepper). Ticked = every repeat tick spawns the same number as the group's initial spawn (e.g. `3 crushers@=`: 3 at once, then 3 more at every tick). Recipe text: `@=` or `@same` (`5 crushers[enraged]@=`). The multiplier sliders scale the repeat like the initial spawn. Unticking turns repeating off for that group; using the repeat stepper or typing a number while ticked leaves "same" mode (the stepper starts from the group's count). A "same" group needs at least 1 initial unit.
- **Clarification of `@N`:** `1 mutant@10` = 1 mutant at once, then **10 additional** mutants on every repeat tick (10 new per tick, not doubling and not cumulative): totals 1, 11, 21, 31... The summary in the wave list reads "(+10 per repeat)". Timing is the wave's "Repeat every" / "Repeat for" steppers.
- Tests: logic +12 (parser, roundtrip, spawner schedule for `@=` and `@10`, multiplier interplay), editor +10 (tick, untick, stepper/popup leaving same mode, zero-count guard).

## 1.4.3
- **Enemy multipliers now always round DOWN** (were half up). 1 unit stays 1 at 190 percent and becomes 2 at exactly 200 (still 2 at 299, 3 at 300); 13 units at 150 percent = 19 (19.5 rounded down), not 20. Implemented as `floor(count * percent / 100 + 1e-9)` with the multiplication first, so decimal results are exact (20 x 115 percent = 23, not 22.999...). Applies to the initial units and to every repeat tick. Consequence: small groups need a higher percentage to grow (1 unit needs 200 percent, 3 units need 134 percent to become 4); below 100 percent small groups vanish sooner (1 unit disappears at anything under 100 percent).
- Tests: logic 191 (the user's cases, boundaries, the float trap, and an exhaustive comparison with integer floor division for every base 0-60 and every slider step, plus through the real spawner).

## 1.4.2
Out-of-memory crash investigation (log `console-2026-09-29-04.44.24-85a45457-*.log`, details in doc 06). The log does not prove RealmsWaves caused it, but three things in the mod were risky and are now hardened:
- **Lua memory guard (new option "Memory guard", default 800 MB, 300-1000):** the game's Lua heap is a fixed 1 GB (`Not enough memory reserved for heap 'lua_heap', reserved: 1073741824`). When the heap is above the guard the mod stops spawning (units stay queued), refuses NEW waves with a message, and logs one warning; before pausing it forces one full garbage collection (at most every 15 s), since a high reading is often uncollected garbage. Spawning resumes by itself when memory drops. `/rw_status` now prints the Lua heap, the guard and whether spawning is paused.
- **Failed position searches are throttled:** when no hidden point was found near the players, the full occlusion query (up to ~27 nav groups and hundreds of points, each allocating) reran on every feed tick (every 0.15 s) for as long as the wave waited. A failed search is now remembered for 1.5 s (about 10 times fewer queries).
- **Reload hygiene:** DMF hooks cannot be removed, so every hot reload (Ctrl+Shift+R) left the old instance's hooks active in the chain, each still counting/subtracting. `mod.on_unload` now retires the old instance: its hooks become pass-throughs, its tracked-unit set and job queues are released.
- **Advice:** the session that crashed had hot-reloaded mods twice, and the heap floor (FpsDoctor) had doubled from 261 to 515 MB, leaving only ~500 MB of headroom. Restart the game instead of hot-reloading when testing, and keep "max enemies alive" and "max per wave" well below the 1000/500 maximums; more units means more Lua memory.
- Tests: logic 178 (memory guard with a faked heap reading: pause/resume/refuse/once-per-15 s GC/configurable/status; throttled searches; retired hooks pass through).

## 1.4.0
- **Enemy number multipliers (mod options, group "Enemy number multipliers"):** three sliders, 0-500 percent (step 5, default 100), applied to every wave when it spawns: **Normal and elite**, **Bosses** (monsters, captains, twins, daemonhost, packmaster), **Specials**. Each group's number (initial units and every repeat tick) is multiplied and rounded half up, so 0 percent removes that type from all waves and 500 gives five times as many (1 x 30 percent = 0, 2 x 30 percent = 1). Classification comes from the game's own breed tags (`Groups.kind` / `Groups.category`: special = `tags.special`, boss = `tags.monster` / `tags.captain` / `tags.cultist_captain`, elite = `tags.elite`; elites count as "normal" for the slider). A group with random alternatives (`a|b`) uses its first alternative's type. If the multipliers remove every enemy of a wave, it is not started and the console explains why.
- **Enemy search in the picker:** "Search enemies" button on the Add enemy screen opens a text box that filters the list live as you type (matches the breed id, every alias such as the old "beastmaster", and the type words boss / monster / captain / special / elite / horde; all words must match). Enter keeps the filter, Esc/Cancel undoes it; the popup sits low on the screen so the list stays visible; the top of the screen shows "Showing N of M enemies matching: ...". Picker rows now show each enemy's type. The search starts empty each time the picker opens.
- **"Count" is now "Weight"** in the editor (column header and the number popup), as requested.
- **Higher limits:** max enemies per wave up to **500** (was 200), max wave enemies alive at once up to **1000** (was 250) in the options (defaults unchanged: 80 and 120). The internal "skip a repeat tick while N units wait" limit went from 200 to 1000 so big waves are not throttled. Reaching 500 per wave needs the multipliers (a wave's base numbers are still capped at 60 per enemy type and 120 in total in the recipe). Large values are heavy for the game (performance and network); the caps are user-tunable.
- **Tests:** logic 147 (kinds/categories, search, multipliers through the real spawner incl. rounding, 0 percent, repeats, one_of, 500-unit waves, options data ranges, a guard that no localization string contains a stray `%`), editor 106 (search flow: live filter, aliases, commit, cancel, clear, no-match, popup position).

## 1.3.0
- **Spread radius (per wave):** each unit spawns at a random point within N metres of the chosen hidden spawn point (default 3 m, 0-30 in the editor), snapped to the nav mesh and rejected if a wall is in the way (falls back to the spawn point itself). Before, every unit used a spawn point exactly, so groups stacked. `Positions.spread` in `spawn/positions.lua`; setting `sp_<key>`.
- **Continuous ("repeating") waves:** an enemy group can add units on every repeat tick: `5 crushers@2` = 5 at once, then 2 more every tick. Per wave: repeat **every** Y seconds (`re_<key>`, default 10) **for** Z seconds (`rf_<key>`, default 60); ticks happen at Y, 2Y, ... up to Z. `0 crushers@2` = repeats only. Works with modifiers and random picks (`3 crushers[enraged]@2`). The repeats respect `max_per_wave` (per tick) and `max_alive`, and a tick is skipped while 200+ units are still waiting. Several waves can run at once. In the editor each enemy row has a second stepper ("Added each repeat"); the initial count may go to 0 while a group repeats; the wave has "Repeat every" and "Repeat for" steppers, and "Spread radius".
- **Fix:** the editor's internal copy of a group dropped the `rep` value on the next save (found by the new tests).
- **Tests:** logic 111 (repeat schedule against a simulated clock, spread through the spawner, `Positions.spread` with stubbed nav queries: radius, uniformity, fallbacks), editor 89 (new steppers, per-row repeat, popups, reset). The editor test now loads the game's real `callback()` from the source clone instead of a lookalike (my earlier stub bound only one argument).
