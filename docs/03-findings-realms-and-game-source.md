# 03. Findings: Realms Server mod and Darktide spawn source

Audited 2026-09-28. Realms 1.0.0-rc2; source clone commit `0f0cb45` (game 1.12.5).
`R` = `mods\Realms\scripts\mods\Realms`. `S` = `Darktide-Source-Code\scripts`. Realms docs (authoritative for mod authors): `mods\Realms\docs\README.md`. The native DLL `bin\darktide-realms.dll` (FFI via `R\runtime\cdef.lua`, `native.lua`) was NOT analysed.

# Part A: Realms

## Host vs client
- No dedicated server: listen server; host is also a normal local player. Vanilla `HOST_TYPES.player` (`S\settings\network\matchmaking_constants.lua:5`; enum: player, mission_server, hub_server, party, singleplay, singleplay_backend_session).
- Host: `R\session\host_session_boot.lua:33-110` creates Realms `ConnectionHost` (`R\connection\connection_host.lua`), native UDP session `Native.start_local_session` (:70), hands it to `Managers.connection` as `_connection_host`. `host_type()` returns `HOST_TYPES.player` (:641); `host_is_dedicated_server()` false (:637).
- Client: `R\session\client_session_boot.lua:105-137`, vanilla `ConnectionClient` with `HOST_TYPES.player` and Realms ticket, tagged `_realms_protocol`. LAN discovery via `LanClient.create_lobby_browser`, `Network.join_lan_lobby`.
- **Recommended detection** (Realms README l.5-34): session `Managers.multiplayer_session:host_type() == HOST_TYPES.player`; role `Managers.connection:is_host()` (`_connection_host ~= nil`) / `is_client()` (`S\managers\multiplayer\connection_manager.lua:244-249`); authoritative logic also needs `Managers.state.game_session` and `game_session:is_server()`.
- Stricter check: `connection._realms_protocol == SessionTicket.PROTOCOL_VERSION` (`R\core\session.lua:216-234`).
- Local single-player with Realms `enable_server`: `MultiplayerSession.boot_singleplayer_session` is hooked and replaced by Realms host boot (`R\Realms.lua:128`, `R\core\session.lua:452`). `enable_hub_server` / `enable_shooting_range_server` can leave hub/Psykhanium as plain `ConnectionSingleplayer` (`host_type` singleplay; `is_host()`/`is_server()` true, Realms API unavailable).
- `shared_state.is_server = params.is_host` (`S\game_states\game\state_gameplay.lua:16`); not dedicated (`:35`). `GameSessionManager:is_server()` returns `_is_server`, set only by `set_session_host` (`S\managers\multiplayer\game_session_manager.lua:166-206`); nil then false on clients.

## Networking
- No new engine RPCs. Realms tunnels JSON through vanilla `rpc_check_mechanism` / `rpc_check_mechanism_reply` (`R\core\session_control.lua:19-20`, framing :187-200, reassembly :304-344, `is_available` :566), with a hello/ready handshake first. Protocols: mod-network, gameplay-control, preparation, chat, latency, profile updates.
- Gameplay traffic is vanilla `GameSession` with network units; **units the host spawns replicate to clients normally**.
- Between missions Realms runs pseudo-state `RealmsPreparationState` (`R\game_states\realms_preparation_state.lua`); no `Managers.state.*` gameplay managers then. Connections persist across missions (`ReusedHostSessionBoot`, `Session.queue_mission_transition` `R\core\session.lua:657`); `Managers.state.*` rebuilt per mission. Late unit RPCs guarded by `R\core\unit_rpc_lifetime.lua`.

## Mod-to-mod messaging (the only channel in this install)
DMF's own network functions are empty stubs (`mods\base\mod_manager.lua:384-410`). Use the Realms API (README l.36-122, exports `R\Realms.lua:23-47`, impl `R\core\mod_network.lua`: register :527, send :555-628, routing :367-419, dispatch :150, manifest :173-239):
- `realms.network_register(mod, rpc_name, cb)`: cb receives `(sender_peer_id, ...)`.
- `realms.network_send(mod, rpc_name, recipient, ...)`: recipients `"local"`, `"host"`, `"all"`, `"others"`, or peer id. Host routes client-to-client.
- `realms.network_is_available()`, `network_on_peer_joined(mod, cb)`, `network_on_peer_left(mod, cb)`, `queue_mission_transition(mod, ctx)` (host only).
- Usage rules: `get_mod("Realms")` in `on_all_mods_loaded`; register there (allowed without a session); **always dot-call**.
- Limits: args JSON-serialisable, max 32 args, max 96 KiB encoded (`R\protocol\mod_network_protocol.lua:9-13`); top-level nil preserved.
- Semantics: only "capable" peers (same mod enabled AND same RPC registered) get broadcasts; direct sends to incapable peers fail `target_rpc_unsupported`. `true` return = accepted for dispatch, not delivered; use reply RPCs for acks. Peer ids are lower-case 16-hex strings. Client `"all"`/`"others"` route via host, no echo to sender. **Host `"all"` DOES dispatch locally first** (loopback; RealmsEvent drops it by host check). One joined and one left callback per mod (re-register replaces; joined replays existing peers on registration). State in `mod:persistent_table("mod_network")` survives hot reload. API stays available through preparation/loading/gameplay/end view, so callbacks can fire with `Managers.state.game_session == nil`.

## Pitfalls for other mods
1. **Managers missing on clients:** `Managers.state.minion_spawn`, `.pacing`, `.horde`, `.bot_nav_transition`, `.voice_over_spawn` are created only when `is_server` (`S\game_states\game\gameplay_sub_states\gameplay_init_step_states\gameplay_init_step_managers.lua:107-113`). Nil-check everything.
2. Host is also the local player; but GhostHost mod removes the host's unit (hooks `should_spawn_dead`, `can_spawn_player`). Guard `Managers.player:local_player(1).player_unit`.
3. Bots: `R\core\bot_backfill.lua` `MAX_BOTS = 7` (:7); hooks `PlayerManager.next_available_local_player_id`, `BotSpawning.spawn_bot_character`, `PlayerUnitSpawnManager` internals. `max_players` 2-12 (`R\Realms_data.lua:68-72`).
4. Host forced single-threaded physics via `GameModeManager.init` (`R\workarounds\local_host_physics.lua:8-14`).
5. `PrivateOutlines` (`R\workarounds\private_outlines.lua`) wraps `OutlineSystem.add_outline/remove_outline`: outlines from other players' server-side buffs hidden on host unless spectating that player.
6. Non-hub mission level seed from loading manager's mission seed (`R\core\mission_seed.lua:8-26`).
7. Hub modes `hub`, `hub_singleplay`, `prologue_hub`, `shooting_range` are special (`R\core\session.lua:22-27`); `mission_preparation` setting skips preparation for them.
8. Realms internals (`mod._session`, `_gameplay_control`, `_session_control`) are not stable: use the documented API only.
9. UNVERIFIED: `Managers.connection.combined_hash` mismatch if mods alter network lookups.

## Havoc conditions / mutators vs. wave units (audited 2026-09-28, source commit `0f0cb45`)
Question from the user: are RealmsWaves' units affected by Havoc conditions (Garden, Final Toll, Warp Rift...), and can conditions be forced on them?

**How conditions reach enemies.** Active mutators come from the mission's circumstance (or the Havoc order's circumstances) loaded by `MutatorManager._load_mutators` (`S\managers\mutator\mutator_manager.lua:26-65`). Most act per minion, at spawn:
- `MinionSpawnManager.spawn_minion` applies the Havoc health modifier itself (`minion_spawn_manager.lua:111-149`, `havoc_extension:get_minion_health_modifier`, survival and circumstance modifiers) and at the end fires `Managers.event:trigger("minion_unit_spawned", unit)` (`:209`). **Any spawn through `spawn_minion` fires it, including ours.**
- Listeners: `MutatorManager._on_minion_unit_spawned` (`:208-214`) -> every loaded mutator's `MutatorBase._on_minion_unit_spawned` (`mutator_base.lua:192-218`), which adds `template.buff_templates` and rolls `random_spawn_buff_templates` per breed chance; and `GameModeExtensionHavoc._on_minion_unit_spawned` (`game_mode_extension_havoc.lua:234-306`: horde hit mass, melee/ranged attack-speed and damage buffs, horde buff config e.g. on-fire poxwalkers).
- Also honoured because we call `spawn_minion`: `replacement_breed` (mutator_replace_breed).

**Per-condition result for wave units:**
| Havoc condition (circumstance / mutator) | Applied to wave units? | Mechanism |
|---|---|---|
| Encroaching Garden (`mutator_encroaching_garden`, buff `havoc_encroaching_garden`) | Yes, by breed chance | `random_spawn_buff_templates` on spawn (`mutator_havoc_templates.lua:153-161`; chances `havoc_mutator_local_settings.lua`: ogryns 0.25-0.35, cultist_captain 1, elites 0.25...) |
| Final Toll / Enraged (`mutator_havoc_enraged`, buff `havoc_enraged_enemies_trigger`) | Yes, by breed chance | same mechanism (`:144-152`) |
| Corrupted enemies, Rotten armor, Parasite headshot, Bolstering, Tougher skin, Sticky poxbursters, No-stagger ritualist | Yes, by breed chance | same mechanism (`:27-172`) |
| Common minions on fire, melee/ranged attack-speed/damage buffs, horde hit mass, health modifiers | Yes | Havoc extension + `spawn_minion` (above) |
| Stimmed minions (yellow/blue/purple) | Yes since 1.1.1 (was a bug caused by the budget bypass; fixed by re-sending `minion_aggroed`, in-game check pending) | `MutatorStimmedMinions` listens to `minion_aggroed` (`mutator_stimmed_minions.lua:15,35-52`), which is fired only inside `PacingManager.add_aggroed_minion` (`pacing_manager.lua:864-866`, when `_should_send_aggro_event`); `spawn/budget_bypass.lua` skips that function for tracked units. | Warp Rift (`mutator_havoc_duplicating_enemies` -> `mutator_duplicating_enemies`) | UNVERIFIED | the circumstance references mutator `mutator_duplicating_enemies` (`havoc_circumstance_template.lua:71-83`) but no template or class with that name exists in this source clone, so its mechanism could not be audited. |
| Horde/pacing overrides (`mutator_havoc_override_horde_pacing_*`), extra trickle hordes, monster spawner/rituals, auric tension | No | they change pacing/spawners, not minions; we bypass pacing |

Nothing is applied when the mission has no such mutator loaded (a normal mission): wave units then get no extra buffs.

## Lua heap limit (observed 2026-09-29)
The engine reserves a fixed 1 GB for the Lua heap (`Not enough memory reserved for heap 'lua_heap', reserved: 1073741824`, assertion `size + commited <= heap->_reserved` in `heap_allocator.cpp:260`); exceeding it is a hard crash, not a slowdown. All mods, all spawned minions' Lua-side state, hot-reloaded mod copies and UI/profile loads share it. In the crashed session the baseline was already 261 MB after the first mission and 515 MB after two hot reloads (FpsDoctor readings), with +200-250 MB transient spikes. `collectgarbage("count")` (KB) reads the same heap, which RealmsWaves' memory guard uses. DMF hooks cannot be removed and DMF does not unhook a reloaded mod's old instance, so anything hooked stays alive across reloads (see `mod.on_unload` in `RealmsWaves.lua`).

## DMF keybinds and text input (audited 2026-09-29)
- DMF keybinds are polled, not event-driven: `dmf.check_keybinds()` runs every frame (`dmf_loader.lua:66`) and evaluates each keybind's device state (`device.pressed(index)`, `keybindings.lua:274-299`). `perform_keybind_action` gates on `is_dmf_input_service_active()`, which is a stub returning `true` (`keybindings.lua:48-51`, "@TODO: link this input service..."). So **no mod keybind is ever blocked by a focused text field**: typing "i" triggers a keybind on "i" (e.g. `hub_hotkey_menus`, which opens the inventory; it only checks `chat_using_input()` and whether its own view is open, `hub_hotkey_menus.lua:48-55`).
- Vanilla hotkeys are different: `UIManager._update_view_hotkeys` only opens hotkey views when NO view is active (`ui_manager.lua:577-587`), and a view that does not allow input passthrough stops the loop (`:570-574`). The editor is an active view, so vanilla hotkeys are already blocked.
- Way to suspend keybinds: hook `get_mod("DMF").check_keybinds` (a plain field on the DMF mod object, called as `dmf.check_keybinds()` so a hook is honoured) and return early. RealmsWaves does this while its popups are open (`RealmsWaves.lua`, flag `text_input_active`). DMF's key-watch mode (`custom_views.lua:348-355`) only affects view toggling, not this.

## Combination pitfalls
- Spawn only when `game_session:is_server()` and `minion_spawn` non-nil.
- **Hub missions:** `BreedLoader` (`S\loading\loaders\breed_loader.lua:26-43`) loads all Breeds for non-hub missions but only player/companion breeds in hubs; spawning regular minions in a hub is unsafe. UNVERIFIED whether shooting range counts as `is_hub`.
- `PacingManager._disabled` is true when no main path (`pacing_manager.lua:125`); direct spawns unaffected.
- For Realms-only behaviour use README predicates or `_realms_protocol`, not just `is_server()`.

## Enemy variants without new breeds (audited 2026-10-01, read-only)
Question: can the wave editor duplicate breed entries (a "Nurgle's Rage" poxwalker, a "Murmur" crusher) with their own colour, health, damage and behaviour, so normal enemies stay untouched? Answer: not as new breeds. Do it as a spawn-time recipe on an EXISTING breed. Conclusions come from reading the source; nothing here was run in the game.
- **Why not duplicate a breed or add a buff template.** `NetworkLookup.breed_names = _create_lookup({}, Breeds)` and `NetworkLookup.buff_templates = _create_lookup({}, BuffTemplates)` (`S\network_lookup\network_lookup.lua:159,161`) are built once at load from the table keys, and `_create_lookup` SORTS the new keys alphabetically (`:85-106`). A new key renumbers every breed or buff after it, so a peer that does not have the same extra keys (a guest without the mod, or another mod version) reads the ids wrongly: the wrong enemy or a crash. Same rule as SoloPlayPurpleStimms ("nothing custom may reach guests"; its harness asserts no custom buff is registered). A breed copy would also be unknown to breed-keyed systems (BreedLoader packages, pacing, VO, scoreboards).
- **Already possible with game names only** (`catalog/groups.lua:76-138`): Purple (Encroaching Garden: extra health, impact resist, heals nearby), Enraged (no stagger, faster melee, hit mass, speed), Red, Blight (Nurgle corruption: lime tint, Nurgle blessing and fly particles, corruption liquid and spread to nearby allies on death), Orange, Pus-Hardened Skin, On Fire, Head Parasite, Purple Stimm, Rotten Armor (Scab Mauler/Rager, Crusher only).
- **Health:** per spawn `param.optional_health_modifier`, read as `init_data.optional_health_modifier or 1` (`minion_unit_template.lua:180`, `spineless_minion_unit_template.lua:111`); `minion_spawn_manager.lua:173-175` adds game-mode modifiers to it. Host side only. The recipe format has no per-group health field yet.
- **Colour:** the buffs tint the model with `Unit.set_vector3_for_materials(unit, "stimmed_color", Vector3(r,g,b), true)` (floats 0-1) BEFORE the `is_server` check, so every peer applies it: Blight 0.373/0.682/0 lime (`S\settings\havoc\havoc_mutator_local_settings.lua:122-126`), Enraged 1/0/0 (`:446-450`), Pus-Hardened Skin its own constant (`havoc_buff_templates.lua:508`). Their stop functions reset it with Vector3(0,0,0), so (0,0,0) means "no tint": the variable acts as an added tint/glow and a truly black model is probably NOT reachable with it (unverified, the shader was not inspected). A custom colour has to be applied by each peer's mod (the host would send unit and colour); a guest without the mod just sees the normal model, which degrades gracefully, unlike an unknown name.
- **Damage and auras:** no spawn parameter. Possible on the host: write the unit's `buff_extension:stat_buffs()` like `havoc_toughened_skin` does (`havoc_buff_templates.lua:528-532`), or run an own interval over the broadphase like `common_minion_on_fire` (`:457-500`). Both untested.
- **Model swaps** (rotten items, parasite heads) need item packages that only the mutator loads; see Rotten Armor above (crash risk).

## Custom mods per group: where each value lives (audited 2026-10-01, read-only, used by `spawn/tuning.lua`)
Source: the 1.13.0 clone. Nothing below was run in the game.
- **Health**: `MinionSpawnManager.spawn_minion` keeps `optional_param_table.optional_health_modifier` and ADDS the game mode's own modifier to it (`S\managers\minion\minion_spawn_manager.lua:137-175`); the unit template multiplies the difficulty's max health by it (`S\extension_systems\unit_templates\minion_unit_template.lua:180-181`, the same in `spineless_minion_unit_template.lua:111-112`). The game passes it itself for monsters, horde and trickle spawns (`specials_pacing.lua:664`, `monster_pacing.lua:907`, `trickle_horde_template.lua:197`).
- **Run speed**: `MinionNavigationExtension.add_movement_modifier(m)` stores a factor; `_recalculate_max_speed` multiplies every factor into `_max_speed`, sets the nav bot's speed and writes the game object field `max_speed_with_modifiers` (`S\extension_systems\navigation\minion_navigation_extension.lua:628-690`). Actions change `_max_speed` with `set_max_speed`, the factors stay; the game uses it for flee/rendezvous (`bt_flee_action.lua:239`).
- **Hit mass**: `HealthExtension.hit_mass` / `set_hit_mass`, the setter also writes the game object field `hit_mass` (`S\extension_systems\health\health_extension.lua:260-268`); the Enraged buff uses it (`S\settings\buff\havoc_buff_templates.lua:1256-1269`, from the BREED's hit mass, so a later Enraged or Final Toll trigger overwrites ours); a stagger multiplies the current value and restores it (`bt_stagger_action.lua:60-70, 233`).
- **Time between attacks (the `melee_attack_speed` stat)**: `stat_buffs.melee_attack_speed` (type `additive_multiplier`, base 1, `buff_settings.lua:863`) is read when a melee attack starts (`bt_melee_attack_action.lua:45-51`). It does NOT speed the animation and does NOT move a damage timing: `_start_attack_anim` only replaces the attack's end with `t + max(duration / speed, T + 0.2667)` (`:259-271` sweeps, `:336-348` others), so the unit leaves the attack earlier and can choose its next action sooner (the blocked action divides its duration by it too, `bt_blocked_action.lua:25-27, 70-71`). For a chained sweep (`attack_sweep_damage_timings` is a list of `{start, stop}` pairs) `T` is the stop of the FIRST pair (`:264-266`), so a high speed ends the attack before the later hits: Plague Ogryn `combo_attack` (`chaos_plague_ogryn_actions.lua:354-435`: 3.56 s, hits end at 1.21 / 1.93 / 2.84 s) at x2.5 ends at 1.48 s; Chaos Spawn `attack_melee_combo` (`chaos_spawn_actions.lua:785-806`) the same. Attacks that are not sweeps use the LAST timing and are fine. The game's own values (Havoc stimm 1.3-1.4, `havoc_mutator_local_settings.lua:378,389,456`) never reach the cut. RealmsWaves corrects it for its own units (`Tuning.fix_attack_end`, hook after `_start_attack_anim`).
- **Gunner fire rate and shots per burst**: `MinionAttack.start_shooting` reads `stat_buffs.ranged_attack_speed` (divides the first-shot delay and every time between shots) and `stat_buffs.minion_num_shots_modifier` (multiplies the burst, except `shoot_template.shotgun_blast`); a fraction rounds up because the loop stops at `shots_fired >= num_shots` (`S\utilities\minion_attack.lua:426-453, 586-611`). The game's own Havoc buffs use 1.25-2.25 (`havoc_buff_templates.lua:2465-2502`). Snipers and the plasma gunner set their own `num_shots` (`bt_sniper_shoot_action.lua:444`, `bt_renegade_plasma_gunner_shoot_action.lua:369`), so the burst does nothing there.
- **Why the stats are re-checked**: `BuffExtensionBase._reset_stat_buffs` resets only the stats some buff modified (`_modified_stats`), then every buff adds its share again (`buff_extension_base.lua:318-354`); minions run that on every buff change and in their update (`minion_buff_extension.lua:97-101, 189-193`). A value written directly (what `havoc_toughened_skin` and Rampaging do, `havoc_buff_templates.lua:244-268, 514-533`) therefore survives until a buff that touches the same stat comes or goes (a player's debuff, Enraged), then it is the buffs' value again. **Correction after the first in-game test (2026-10-01):** while any buff touches the unit's stats (a mission-wide Havoc modifier does) the extension recomputes them EVERY frame, so a written value is dropped every frame; RealmsWaves puts its factor back right after each recompute with a post-hook on `BuffExtensionBase._update_stat_buffs_and_keywords` (and a 0.25 s check as a fallback).
- **Size**: the Rampaging buff scales its unit with `Unit.set_local_scale(unit, 1, Vector3(1,1,1) * scale)` (`havoc_buff_templates.lua:247-249`, up to 1.08), in `start_func` outside the `is_server` check, so every peer runs it because the buff is synced. No minion code scales anything else, and nothing syncs a scale by itself. The network id of a unit: `Managers.state.unit_spawner:game_object_id(unit)` on the host, `unit_exists(id)` / `unit(id)` on a client (`S\foundation\managers\unit_spawner\unit_spawner_manager.lua:604, 650, 664`). Unverified: whether the hit zones (physics actors) follow the scale, and how a large scale behaves with the unit's mover and navigation.
- **A hook on a parent class does not reach its subclasses (2026-10-02, found by the user's console log)**: `class(name, super_name)` copies every method of the parent into the new class table when the subclass is created (`foundation/utilities/class.lua:100-106`, all but `new`, `delete`, `super`, `__index`, `__class_name`, `__interfaces`). DMF replaces the method in ONE class table, so `mod:hook("BuffExtensionBase", "_update_stat_buffs_and_keywords", ...)` is not seen by `MinionBuffExtension` (its own copy, `minion_buff_extension.lua:101` calls `self:_update_stat_buffs_and_keywords(t)`). Hook the class of the object you care about; hook both when unsure.
- **Stat recompute of a minion (2026-10-02)**: `MinionBuffExtension.update` recomputes the stats every frame (`:101`); the class has `UPDATE_DISABLED_BY_DEFAULT = true`, so a unit with no buff is presumably not updated at all (the switch that turns it on was not read). `_reset_stat_buffs` sets back to the base value only the stats listed in `stat_buffs._modified_stats` (`buff_extension_base.lua:318-328`); every buff then adds (`additive_multiplier`: `+`, `multiplicative_multiplier`: `*`, `max_value`: `math.max`, `buff.lua:714-727`) and lists its stats as modified (`:730`). `ranged_attack_speed` is additive (`buff_settings.lua:939`, base 1), `minion_num_shots_modifier` multiplicative (`:890`). A stat written by a mod must also be listed in `_modified_stats` or the next recompute adds the buffs on top of it. `havoc_ranged_attack_speed_05` is `ranged_attack_speed +0.3` and `minion_num_shots_modifier x2.25` (`havoc_buff_templates.lua:2497-2504`): a Havoc unit reads speed 1.3 and 2.25 times the shots.
- **Burster explosion (2026-10-02)**: `BtChaosPoxwalkerExplodeAction.enter` calls `Explosion.create_explosion(world, physics_world, position, rotation, unit, explosion_template, power_level, 1, nil, false, ...)` with the action's fixed template (`poxwalker_bomber`: `radius 6`, `min_radius 3`, `close_radius 3`, `min_close_radius 1`, `scalable_radius = true`; `poxwalker_bomber_mild` half of it, `minion_explosion_templates.lua:88-135`). The charge level is the constant 1 and the attack type nil, so neither the lerp between `min_radius` and `radius` nor `explosion_radius_modifier` (only for attack type "explosion", `explosion.lua:484-500`) changes it. `create_explosion` sends the radius vector to the clients (`:58-71`), so a bigger radius reaches them without anything else.
- **Animation speed of a minion, the in-game answer (2026-10-02)**: `/rw_anim` on cultist berzerker, plague ogryn and chaos spawn found only the variables `anim_move_speed` and `moving_attack_fwd_speed`; the engine's `Unit` table has 50 functions about animation, speed, time, scale or rate (`animation_set_time`, `animation_get_time`, `animation_set_variable`, `crossfade_animation_set_speed`, `set_simple_animation_speed`, `play_simple_animation`, ...); the speed functions belong to simple animations and crossfades, not to the state machine of an enemy. No per-unit attack animation speed.
- **Animation speed of a minion (asked 2026-10-01, NOT available in the scripts)**: `MinionAnimationExtension` offers `anim_event`, `anim_event_with_variable_float`, `set_variable` (only variables listed in the breed's `animation_variables`, in practice `anim_move_speed` and `moving_attack_fwd_speed`, which steer locomotion blends) and nothing else (`minion_animation_extension.lua:95-148`); a search of the whole `scripts` tree finds no call of a unit-level animation speed (`Unit.animation_set_speed`, `set_animation_speed`, ...); the only `Unit.animation_*` functions used are `set_variable`, `event`, `find_variable`, `get/set_state`, `set_time`, `set_animation`, `get_variable_min_max` and a few more. The animation state machines are binary, so a speed variable for attacks may exist but cannot be read offline. `/rw_anim` (see the CHANGELOG) asks the running game. Scaling the damage timings of the attack without the animation would make the hit land before the wind-up on screen, so it is not a substitute.

### Recovery review, 2026-10-03
Realms mod_network.receive_host_request relays client requests addressed to others while preserving sender_peer_id (core/mod_network.lua:367-386). Therefore a valid sender string alone does not establish that rw_state, rw_welcome or rw_scale came from the host. Protocol now matches Managers.connection:host() before decoding or forwarding these messages; missing/closing connections reject them. BuffExtensionBase._reset_stat_buffs resets the modified keys before adding buffs (318-354); equal numeric values do not establish that a write was retained. A minion reset hook marks a fresh recompute and consumes that marker once across the post-hooks. No new network lookup, breed or buff data is introduced.
